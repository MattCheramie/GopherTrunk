*Part 6 of **Squelch**, a 14-part deep dive into GopherTrunk's conventional
scanner — the scan list with no control channel to announce a call — and
every gate that decides when a channel opens.
[Part 5]({{ '/blog/deep-dives/squelch-05-ctcss/' | relative_url }}) separated
CTCSS tones 2.3 Hz apart with an exact Goertzel bin and its neighbours. This
part is the tone gate's digital sibling: a 23-bit word looped under the
voice, and a detector with no clock recovery, no word sync and no level
threshold. Why the first DCS detector never matched a radio
([#1184](https://github.com/MattCheramie/GopherTrunk/issues/1184)) is
[Rebuilt From the Air Part 3]({{ '/blog/solution-postmortem/rebuilt-from-the-air-03-ctcss-dcs-tone-gates/' | relative_url }})'s
story; this post is the one that does.*

> **TL;DR:** A DCS gate is `DCSDetector` in
> `internal/scanner/conventional/dcs.go`. It shares Part 5's `toneFrontEnd`,
> low-passes the discriminator at 250 Hz, slices against the midpoint of the
> recent high and low (a carrier offset is DC), and integrates each bit at
> `dcsPhases` = 4 staggered clock phases. Each phase slides a 23-bit window
> past 46 targets — 23 rotations × 2 senses from `tonecode.DCSRotations` —
> at Hamming distance ≤ 2, and a match must hold `dcsConfirmBits` = 16 bits
> (~120 ms). On air the word is bit 0 first: C0..C8, 0 0 1, P0..P10; code
> 023 is `0x763813`. Only `tone.dcs_polarity` opens the gate; 023N and 047I
> are the same bits and always will be. The scan window grows to 600 ms.
> On-air verified 24 Sep: D025N reads `nrz_inverted=false`.

**Key takeaways**

- **The layout is the decoder.** Code low bit first, a fixed 0 0 1, eleven
  parity bits: get the order wrong and every self-made test still passes
  while no radio ever matches.
- **Brute force replaces two loops.** Four free-running bit phases stand in
  for clock recovery and 23 rotations stand in for word sync — cheap at
  134.4 bit/s.
- **Aliases are a property of DCS.** A looped word read from another start
  bit is another code (023 ≡ 340 ≡ 766) and its complement is another code's
  word (023N ≡ 047I). No receiver can tell them apart.
- **Polarity is a setting, and the log says when it is wrong.** Only the
  configured sense opens; the other is tracked just to WARN once per
  channel.

## A data stream under the voice

[DCS]({{ '/reference/dcs/' | relative_url }}) — Digital-Coded Squelch, also
called DPL — does the job of
[CTCSS]({{ '/reference/ctcss/' | relative_url }}) with bits instead of a
sine. While the transmitter is keyed it adds a 134.4 bit/s NRZ stream below
the voice band: the carrier sits a few hundred hertz to one side for a 1 and
to the other for a 0. The stream is one 23-bit word, sent over and over —
171 ms per word, nearly six times a second — with no preamble and no marker
between repeats. The file header in `dcs.go` draws the consequence: "a
receiver can lock onto any of its 23 cyclic rotations".

The gate inherits everything Part 5 established. It uses the same
`toneFrontEnd`, so the discriminator output is in radians per sample at
48 kHz whatever the SDR's rate, and the channel filter has already removed
the rest of the band. It answers the same question — is this transmission
*mine* — and plugs into the scanner through the same three-method
`toneDetector`. What differs is everything after the discriminator.
[Protocol Decoders Part 9]({{ '/blog/deep-dives/protocol-decoders-09-conventional-wideband/' | relative_url }})
described the DCS detector as "a tracked follow-up"; this is that follow-up,
in its second and current form.

The word has three parts, in the order they are sent. First the code: the
three octal digits an operator programs are nine bits, sent **least
significant bit first**. Then a fixed 0 0 1. Then eleven parity bits that
make the whole thing a codeword of the
[Golay]({{ '/reference/golay-code/' | relative_url }})(23,12) code — the
family
[SDR in Pure Go Part 9]({{ '/blog/deep-dives/sdr-internals-09-framing-fec/' | relative_url }})
introduced — in which any two codewords differ in at least seven places.
`tonecode.DCSCodeword` builds it:

```go
// internal/scanner/conventional/tonecode/tonecode.go (shape)
const dcsGolayPoly = 0xAE3 // x^11+x^9+x^7+x^6+x^5+x+1

data := uint32(c) | 1<<11 // the 9-bit code + the fixed 0 0 1
var reg uint32
for i := 0; i < 12; i++ { // data bits in transmit order
	fb := (data>>uint(i))&1 ^ (reg>>10)&1
	reg = (reg << 1) & 0x7FF
	if fb != 0 {
		reg ^= dcsGolayPoly & 0x7FF
	}
}
// bits 12..22 on air are reg, most significant bit first
```

Bit `i` of the result is the `i`-th bit transmitted, and that convention is
kept everywhere downstream. It is also where this detector's predecessor
went wrong. The header of `dcs.go` records it without softening: the old
codeword put the code in the high bits and a 1 0 0 sync in the low bits and
slid bits in MSB-first, and "its test synthesizer transmitted that same
invented layout, so every unit test passed". That is
[the self-consistent trap]({{ '/blog/solution-postmortem/from-the-issue-tracker-20-self-consistent-trap/' | relative_url }})
in its purest form, and the repair is an independent reference.
`refDCSWord` in `dcs_reference_test.go` builds the same word from the
eleven parity equations as published — P0 = C0+C1+C2+C3+C4+C7 and ten
more — "written independently of dcsCodewordFromOctal on purpose", and
`TestDCSCodewordMatchesPublishedParity` holds all 512 codes to it, plus the
literal `0x763813` for 023.

## Slicing without a level

After the front end the detector low-passes at 250 Hz — "above the 134.4
baud NRZ fundamental and below the voice band" — and has to turn a wobbling
voltage into bits. The obvious slicer, the sign of the discriminator, is
what the old detector used, and a mistuned carrier defeats it completely.
A carrier offset is a constant added to the discriminator output; a few
hundred hertz of tuner error is as large as the DCS deviation itself, so
both NRZ levels land on the same side of zero and every bit reads the same.

`trackLevel` replaces zero with a measured centre:

```go
// internal/scanner/conventional/dcs.go (shape)
d.blkHi = math.Max(d.blkHi, x) // extremes over half a word
d.blkLo = math.Min(d.blkLo, x)
if d.blkN++; d.blkN >= d.blkLen {
	hi, lo := d.blkHi, d.blkLo // widened by the previous block's
	d.mid = (hi + lo) / 2
}
// per bit, per phase: integrate (x − d.mid); the sign of the sum is the bit
```

The comment gives the reason it is safe: "A DCS word always holds both bit
values, so the extremes bracket the NRZ levels whatever DC the carrier
offset adds." Nothing in the decision is an amplitude. The bit is the sign
of an integral of the level-centred signal over one bit period, so a strong
tone and a weak one slice identically — the same scale-free property the
series borrows from
[The Analog Edge Part 13]({{ '/blog/tutorials/analog-edge-13-coherence-not-dbfs/' | relative_url }}).

The bit clock gets the same treatment: no loop at all. `dcsPhases` is 4, and
the constant's comment is the whole design note — "There is no clock
recovery: one of four phases is always within 1/8 bit of the transmitter's,
which is plenty at 134.4 baud." Four integrate-and-dump accumulators run a
quarter bit apart (a bit is about 357 samples at 48 kHz), and each keeps its
own window of the last 23 bits, shifting so that "the oldest bit ends up in
bit 0" and a window aligned to a word boundary is the codeword itself.

## Forty-six targets, sixteen bits of patience

Each phase compares its window against a precomputed list.
`tonecode.DCSRotations` returns 46 words: the 23 cyclic rotations of the
target, each followed by its bit-complement, so even entries are the normal
sense and odd entries the inverted one. `checkTargets` XORs and counts bits
— "46 XOR + popcount ops" — and accepts a window within
`tonecode.DCSMatchDistance` = 2 bits of a rotation in an accepted sense.
Two bits of tolerance are safe because Golay codewords are seven apart: a
window two bits from one word is still five from any other.

Tolerance has a price on noise. Of the 8 388 608 possible windows, 277 lie
within two bits of any one target (1 + 23 + 253), and four phases look once
per bit, so an isolated chance match is not rare enough to open a squelch
on. The gate therefore demands persistence. `dcsConfirmBits` is 16: "A true
stream matches at every bit; noise that happens to match one window keeps
matching with probability ~1/2 per bit, so 16 bits cuts the false-open rate
by ~2^16." Sixteen bits is about 120 ms. Once open, the gate closes when no
phase has matched for a full word.

Add it up — half a word to set the slicing level, a 23-bit window, sixteen
confirming bits, filter delay — and the first report arrives well after the
250 ms a CTCSS block needs. `dcsMinDwell` is 600 ms, and as in Part 5 the
scanner raises the scan window for the *whole* list to it when any channel
is DCS-gated. The other costs carry over unchanged: the call starts when
the gate confirms, not when the carrier appears, and data decoders ignore
the gate.

## Aliases and polarity

Two things about DCS look like detector bugs and are not.

**Aliases.** The word is cyclic and the receiver has no idea where it
starts. Read the 023 word from a different start bit and, at two of the 23
positions, the fixed 0 0 1 and a valid parity happen to line up again: the
same bits on air are also code 340 and code 766. Complement the 023 word
and it is a rotation of code 047's. `TestDCSCodewordAliasesMatchReferenceTables`
checks both properties against published tables — 023 ≡ 340 ≡ 766,
054 ≡ 405 ≡ 675, and inverted 023, 754 and 627 reading as 047, 116 and
031 — as evidence the construction is the real one. The constructor's
comment draws the operational conclusion: every gate also opens on its
alias, "inherent in DCS, not tellable apart on air". A normal 023 gate
opens on a radio sending 047 inverted, and nothing should be done about it.
What can be done is done in config: `tonecode.Overlap` stops two logical
channels on one shared frequency from using gates that one transmission
would open, and its error names "a DCS alias such as 023N = 047I".

**Polarity.** Whether a 1 is sent as a rise or a fall in frequency is a
radio setting, the N or I after the code. The convention was pinned on air
on 24 Sep, with the reporter's Kenwood NX-300 and NX-5000 radios and a
service monitor: a radio set to D025N sends its 1 bits as *positive*
deviation, which the detector reports as `nrz_inverted=false`; D025I reads
`true`. Until that run the gate accepted both senses and logged which one
matched. Since it, only the configured sense opens, through one more key in
the `tone:` block of
[Operator's Cookbook Part 6]({{ '/blog/tutorials/operator-cookbook-06-analog-fm-tone-out/' | relative_url }}):

```yaml
scanner:
  conventional:
    - label: "UHF Simplex"
      frequency_hz: 447100000
      mode: nfm
      squelch_dbfs: -50
      tone:
        mode: dcs
        dcs_code: "025"
        dcs_polarity: normal   # normal (radio "D025N", default) | inverted | both
```

The opposite sense is still tracked, with the same sixteen-bit streak, but
only as evidence. When it accumulates, `TakeOppositeHeard` fires and the
scanner logs, once per channel, `conv: DCS code heard with the opposite
polarity; gate kept shut — set tone.dcs_polarity to match the radio (N =
normal, I = inverted) or both`, with `dcs_polarity` and `heard` fields. An
open logs `conv: DCS gate opened` with `dcs_code` and `nrz_inverted`. Two
honest footnotes follow from the alias rule. `both` on 023 also opens on
047N. And because 047N *is* 023I on air, a 047N radio on a normal 023
channel raises the polarity hint too; the detector cannot know which the
operator meant.

## What pins it

**The reference.** The parity equations and alias tables above come from
published sources independent of the encoder, so the codeword is
**reference-pinned** for all 512 codes.

**The production rate.** `synthDCSOnAir` transmits the *reference* word the
way a radio does — bit 0 first, with a carrier offset, noise, and a random
start bit and sub-bit phase. `TestDCSDetectsOnAirWordAtSDRRate` runs codes
023, 754 and 411 in both senses at 2 400 000 samples per second, 350 Hz of
deviation and 600 Hz off frequency, and demands continuous detection after
`dcsMinDwell`. `TestDCSRejectsOtherCodeAndBareCarrierAtSDRRate` covers the
other side.

**Polarity.** `TestDCSGateAcceptsOnlyConfiguredPolarity` walks the six
combinations of setting and transmitted sense, including the mismatch flag;
`TestDCSDefaultGateIgnoresAliasedCode` checks that a plain 023 gate stays
shut on 047N; `TestWarnDCSOppositePolarityOncePerChannel` counts the WARN.

Status: **on-air verified** on 24 Sep, alongside the CTCSS gate. One gap is
worth naming: unlike CTCSS there is no DCS real-air slice in `testdata/`,
so the regression suite rests on the published reference and synthetic
transmissions.

### How DCS shaped the Go code

- **The codeword lives outside the detector.** `tonecode` has no imports, so
  config validation and the DSP share one definition and the test holds a
  third, independent one.
- **Polarity is a type.** `DCSPolarity` and its `accepts` method make
  "which sense opens" an explicit decision instead of a side effect of the
  target list.
- **Rejected evidence is still reported.** A recognised-but-refused signal
  becomes a single WARN that carries its own fix.
- **Brute force where it is cheap.** Four phases × 46 comparisons per bit is
  trivial work at 134.4 bit/s, and there is no loop to fall out of lock.

## FAQ

**How does a DCS decoder know where the 23-bit word starts?**
It does not need to. GopherTrunk compares every 23-bit window against all 23
cyclic rotations of the target word, so a window that starts anywhere in the
loop matches. Four staggered bit-clock phases remove the need for clock
recovery in the same way.

**Why does my DCS 023 channel open on a radio set to 047 inverted?**
Because they are the same bits on air: the complement of the 023 word is a
rotation of the 047 word. No receiver can distinguish them, GopherTrunk
included, and config validation refuses to put the two on one shared
frequency.

**What does nrz_inverted mean in the DCS gate opened log line?**
It is the sense of the match: `false` when the code's 1 bits arrived as
positive frequency deviation, which is what a radio set to N (for example
D025N) sends, and `true` for a radio set to I. Set `tone.dcs_polarity` to
match.

**How long does a DCS gate take to open?**
A match must hold for 16 consecutive bits, about 120 ms, after half a word
to set the slicing level and a full 23-bit window. The scanner allows
600 ms per scan window on a list with a DCS channel.

**Is the DCS gate verified on air?**
Yes — on-air verified on 24 Sep with Kenwood NX-300 and NX-5000 radios and
a service monitor, which also pinned the polarity convention. The codeword
is pinned against published parity equations for all 512 codes; there is no
committed real-air DCS capture.
